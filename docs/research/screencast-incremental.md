# 画面流增量更新调研（#21）

调研问题：画面流模式目前是「每帧全量 JPEG」，能否做帧间差分（只送变化块）？

## 实测数据（2026-10-18，真机 ChatGPT.app 主 shell）

| 场景 | 帧数（10s） | 导线字节（base64） | 平均带宽 |
|------|------|------|------|
| 页面「静置」 | 508 | 154 MB | **15.1 MB/s** |
| 局部闪烁（200×100 元素） | 412 | 124 MB | **12.1 MB/s** |

数据源：docs/research/screencast-bandwidth-20261018204709.md
（tool/measure_screencast_real.dart，q60 / everyNthFrame=1 / base64 导线长度）。

对照：DOM 重绘模式同窗口稳态 **0.02 KB/s**（docs/research/dom-bandwidth-20261018201658.md）——相差约 **75 万倍**。

## 关键发现

1. **「静置」不静**：真机主 shell 即使无用户操作也有持续的画面变化（背景动画/流媒体内容），CDP screencast 按画面变化出帧，因此实测 508 帧/10s ≈ 51fps 全速出帧。
2. **局部变化不省带宽**：200×100 的闪烁元素触发的仍是全量 JPEG 帧（协议层面没有 dirty rect），带宽与全屏变化几乎相同（12.1 vs 15.1 MB/s，差距来自帧内容复杂度而非面积）。
3. 「完全重刷」的带宽担忧在真机上**成立且严重**——但受害面是画面流模式，DOM 模式不受影响。

## 方案对比

| 方案 | 带宽收益 | 实现成本 | 风险 |
|------|---------|---------|------|
| A. 宿主端像素 diff + 分块 JPEG | 高（局部变化场景 10×+） | 高：Dart 侧逐帧 JPEG 解码（image 包）在 50fps 1280×1024 下 CPU 成本高；分块协议、远程端合成都要新写 | 宿主 CPU 成为新瓶颈；协议复杂度大增 |
| B. CDP 原生能力 | — | — | **不存在**：screencast 无 dirty-rect 输出 |
| C. 视频编码（H.264/WebRTC） | 极高（10-100×） | 很高：独立编码进程或原生模块，偏离 CDP 纯注入路线 | 架构级变更 |
| D. 不做帧差分，用既有旋钮 + 模式分工 | 中 | 零 | 无 |

## 建议：D（不做帧差分）

理由：

1. **模式分工已覆盖**：画面流定位是兜底（原生菜单/对话框/canvas 盲区），常态操作走 DOM 重绘（0.02 KB/s）。为兜底模式投入视频级优化不划算。
2. 既有旋钮足够止血：`everyNthFrame`（默认 4 ≈ 12fps）+ `quality` + `maxWidth/maxHeight` 降分辨率，可把 15 MB/s 压到 1-2 MB/s。
3. 若未来画面流升级为主力模式，正确解法是 C（视频编码），不是 A——A 是用 CPU 和协议复杂度换一半收益的中间态。
4. 本机/局域网场景 1-2 MB/s 完全可接受；公网场景按 grilling 决策不在范围内（需要时走 tailscale）。

## 遗留旋钮建议（可选小改进，非本票范围）

- 画面流会话可考虑默认 `maxWidth: 1280` 封顶，防止高分屏下带宽失控（真机 1280 视口已接近上限，影响暂小）。
